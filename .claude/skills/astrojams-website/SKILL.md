# astrojams website

The site markets the owner's astrojams apps: everything on the personal James Thompson App Store team, from calm
news to games. Every app has a landing page at `https://astrojams-apps.vercel.app/<slug>/`, the link to share. An app
without a website of its own uses that page as its App Store **Marketing URL**; an app with its own site keeps it and
its page here links to it. The owner asked never to have to point out that the site is out of date: keeping it current
is this skill's job, and routine updates from verified store facts are authorized to ship without asking.

| Thing | Where |
|---|---|
| Site repository | `/Volumes/ssd/code/app-sites` (GitHub `astrojams1/app-sites`, private). This site is `sites/astrojams`; the Ouro site is `sites/ouro`; both are built from `packages/showcase` |
| Project home (research, captures, staging) | `/Volumes/ssd/projects/astrojams-apps/` |
| Curated catalog | `sites/astrojams/src/data/apps.json` (copy, theme, screenshots, FAQ, `excluded` records, and the site's `brand` and `copy`) |

Home is a colour stage (`packages/showcase/src/components/Stage.astro`, scroll maths in `packages/showcase/src/lib/stage.js`); app pages are `packages/showcase/src/pages/[slug].astro` |

| Audit | `node <this skill>/scripts/audit.mjs` (Node 22, no dependencies, read-only) |

What is automatic already: a GitHub workflow runs `sync:store` every six hours, commits `store.json` changes (Vercel
deploys them) and opens the issue **"astrojams website needs an update"** in `astrojams1/app-sites` when Apple lists an app on the team that the
catalog neither shows nor excludes, or a live one disappears. A release therefore flips the badge on its own;
everything else (new apps, unreleased apps, copy, screenshots) needs this skill.

## Run it

Use Node 22 (`PATH=/opt/homebrew/opt/node@22/bin:$PATH` on the owner's Mac). Record the run in the shared activity
ledger as the owner's `AGENTS.md` requires: one `run_id`, `skill: "astrojams-website"`, events `start`, each `action`
or `finding`, `verify`, `end`, with targets, evidence (commit, deployment id, URLs) and anything skipped. Use the
helper `/Users/astro/.codex/skills/mac-memory-maintenance/scripts/ledger.py`.

1. **Sync.** At the site repository's root: `git pull --ff-only`, `npm ci`, read its `AGENTS.md`, and check open
   issues (`gh issue list --repo astrojams1/app-sites`; this site's carry "astrojams" in the title). Preserve anyone else's uncommitted work.
2. **Refresh public status.** `npm run sync:store -w sites/astrojams`. Exit 2 lists a live app on the team the site does not know; exit
   3 a listed app Apple no longer returns.
3. **Audit App Store Connect.** `node <skill>/scripts/audit.mjs` (`--json` for detail). It reads the App Store Connect
   key from the 1Password item named in any personal-team app's `app-release.config.json`, using the token rules in
   the owner's `AGENTS.md`; never print or log a value. It prints every record on the team with its latest version
   state, whether the site shows, excludes or misses it, the app's repository (a main checkout over its worktrees),
   and **Actions**: new records, renamed apps or subtitles, released apps not yet synced, catalog apps that left the
   team. **Follow-ups** list app repositories whose store data has no `listing.marketingUrl`.
4. **Decide each new record.** Add every real app the owner is shipping on this team, games and tools alike; it
   appears as soon as it has an App Store Connect record and a listing or README to draw from, and does not wait for
   review. A duplicate, placeholder or test record goes in `excluded` with a one-line reason so no later audit asks
   again. Ask the owner only when it is genuinely unclear whether a record is a real app.
5. **Write or refresh the entry** from the app's own listing (its repository's store data, else App Store Connect),
   its README and its website, following [content](references/content.md): headline, pitch, audience, features, trust
   points, FAQ, theme, and a `spotlight` when the app's story needs one. Label anything still in development as such.
6. **Source the images** per [assets](references/assets.md): a 1024px icon, 2 to 6 real screenshots, alt text.
7. **Verify** (below), then **ship**: commit to `main` with a message naming the apps changed, push, and confirm the
   Vercel production deployment for that commit is `READY` and the live pages show the change.
8. **Close the loop.** Close the GitHub issue with a comment saying what changed. For each follow-up, set the app's
   `listing.marketingUrl` in its repository through that repository's normal branch or pull-request flow, or record
   it as the next action in its release ledger when the repository has unrelated work in progress; app-release sends
   it with that app's next `asc.mjs listing`. Never replace a marketing URL the app already has, and never push
   listing changes to App Store Connect from this skill.

A design or structure change (new section, new layout, new dependency) goes on a branch with a pull request and
screenshots for the owner; content and asset updates go straight to `main` once verification passes. Anything in
`packages/showcase` changes the Ouro site too: build and look at both sites, put screenshots of both in the pull
request, and say so in the report. A difference that is only words or brand belongs in `site.copy` or `site.brand`,
not in a branch of the shared code.

## Verify

- At the repository root, `npm test` and `npm run build` (both sites) pass. `npm run check` (part of the build) fails on missing fields or images, poor
  colour contrast and App Store wording Apple forbids; fix the data, never weaken the check to pass.
- `npm run preview -w sites/astrojams` and look at every changed page at 1280px and 375px wide. Sections fade in on scroll, so wait a
  second (or add `is-visible` to `.reveal` elements) before judging a blank area. On the phone width,
  `document.documentElement.scrollWidth` must equal the viewport width: no sideways scrolling.
- After any change that touches the home page (an app added, removed or reordered, new screenshots, stage code), run
  the browser scroll check: load `packages/showcase/tests/browser/stage-scroll.js` into the home page of the preview and
  `await stageScrollCheck()` at 1440×900 and 375×812. It must return `ok: true`. A full run takes minutes; start it
  without awaiting (store the result on `window`) and poll, since evaluation tools time out.
- Every iPhone browser, Chrome included, runs WebKit, and the browser pane is Chromium. After a layout or stage change,
  also open the preview in Mobile Safari on an iOS Simulator (follow the owner's simulator storage and lease rules).
- Open `sites/astrojams/dist/og/<slug>.png` (the link-preview card) and check the headline, icon and status fit.
- A live app shows Apple's black badge, its rating once five people have rated it, a QR code on desktop and the
  sticky bar on phones; a coming-soon app shows "Coming soon to the App Store" and never the badge.
- After deploying: `curl -s -o /dev/null -w '%{http_code}' https://astrojams-apps.vercel.app/<slug>/` is 200.

## Gotchas

- Space Worms' bundle identifier is `com.spaceworms.app`, not `com.astrojams.*`, but it is on the personal team and
  belongs on the site. Team membership decides, not the bundle prefix.
- Several app folders under `/Volumes/ssd/code` are worktrees of one app (Space Worms, Importron, Newsworthy). The
  audit reports the main checkout when it is there; Importron's main checkout lives in `/Users/astro/code/importron`,
  so the audit names its SSD worktree instead.
- Rhythm and Data Center are Capacitor web apps with no store screenshots yet. Their screenshots came from Data
  Center's `docs/images` and a headless capture of Rhythm's built `dist/` at iPhone size; replace both with the real
  store screenshots once they exist.
- Three of the five themes are dark. Screenshots carry a faint ring in the page's ink so a dark screen keeps its edge
  on a dark page; keep it when restyling.
- Apps with their own websites (Newsworthy, Space Worms) keep them as their Marketing URL; the audit only flags an
  app with none. Change that only if the owner asks.
- The public lookup can trail Apple's release by hours. A released app still "coming soon" right after release needs
  only `sync:store` later, not a manual status edit.
- Link-preview cards are drawn by satori from `.woff` Latin fonts: keep their text to Latin characters, no emoji or ★.
- Astro 7.4 needs Node 22.22 or later; the Homebrew `node@22` is new enough, the default `node` (20) is not.
